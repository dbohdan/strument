# Does calling bash the tool for running the project make models run it?

**Status: design.** Written and committed on 2026-11-03, before the pilot and
before any model call. Nothing here has been run yet. A pilot section and a
results section will follow below; changes made after the pilot go in a
`preregistration.md` beside this file, committed before the main run.

## Why

A third-party comparison on `bitstillery/mithril` (2026-11; the TypeScript
Mithril line with signals) asked two models how its state proxy tracks nested
objects and arrays. Both had one session in Strument and one in another
harness. An Opus 5.5 reviewer then checked every claim against verified
behavior. Its finding: **running code was the largest accuracy lever** for both
models.
- MiMo-V2.6-Pro, reading only, made two mechanical errors. In Strument, its
  single `bun -e` probe printed output that corrected both.
- DeepSeek-V4.1-Flash wrote four probe scripts and found the one-level bound
  on notifications that no reading-only run found.

The reviewer guessed that Strument's prompt was what elicited the execution.
It is not. The phrase it quoted ("confirm the actual runtime behavior rather
than reasoning only from the source") is DeepSeek's own reasoning. What the
prompt says about bash points the other way:

> - bash runs a shell command, and the user is asked before it runs. Reach for
>   it only for work the other tools don't cover; reading and searching have
>   their own tools.

"Only" frames bash as a last resort. Meanwhile `run_code`, listed first, "changes
nothing and needs no permission". For an investigation, that steers toward
reading. The execution in those sessions happened *despite* the bullet. The
other three suggestions from the review — an edge-case step, a buggy-probe rule
and a hedge rule — are out of scope here. They are one arm each, for later.

Two sessions are anecdotes. So this trial asks: does rewording the bullet
raise how often models execute code to answer a question about behavior, does
that make the answers more correct, and what does it cost where execution
adds nothing?

## Arms

Both arms are built from the same commit, which carries the `run_code` fixes
of `564be22`. They differ in exactly one string in
`internal/prompts/prompts.go`: the bash bullet of the tool prompt.

- **A (HEAD):** the text quoted above.
- **B:** "bash runs a shell command, and the user is asked before it runs. Use
  it to run things: the project's tests, its code, a short script that checks
  how something actually behaves. Reading and searching have their own tools."

B keeps A's two facts (the user is asked; reading and searching are
elsewhere), drops the "only", and gives the felt need ("check how something
behaves") a tool. This is the mapping
[`2026-08-symbol-uptake`](../2026-08-symbol-uptake/) found moves uptake.

The runner builds one binary per arm and diffs the two rendered system prompts.
It refuses to run unless they differ in that bullet and nowhere else (handbook
§7).

## Fixture

The fixture is an invented, self-contained JavaScript project, so there is
nothing to clone and no dependency to install. It is an ES module library
(`package.json` with `"type": "module"`, tests on `node --test`) of about 300
lines across five files, with a README and a short design note. It is
generated by `data/fixture.py` and committed before the main run.

JavaScript on purpose:
- It is the language where `run_code` was mistaken for running the project, so
  the trial also counts that confusion under the shipped clause.
- Node is installed wherever this trial runs.

Two tasks, each asked as the single user turn of a fresh session:

- **run** (the effect). This is a question about behavior: what a public
  function returns for a given input. The answer depends on two or three
  JavaScript behaviors that are easy to get wrong when reading, each placed
  where it changes the result. Candidates are the default `sort` comparing as
  strings, `map(parseInt)` passing the index as the radix, integer-like object
  keys enumerating first, and `new Date("YYYY-MM-DD")` parsing as UTC. It is
  answerable by careful reading, so execution is a means, not a requirement.
  It ends with "Finish with one line, `RESULT: ` followed by the value as
  JSON."
- **read** (the counter). This asks where a behavior is implemented and what
  its documented contract is, with the answer as a file and a function name.
  Running code answers nothing here that reading doesn't. It ends with
  "Finish with one line, `RESULT: <file>:<function>`."

The fixture must assert its own key (handbook §26): `fixture.py` runs the
function under Node and checks that the run task's answer is what it says. It
also checks that each trap changes that answer: with the trap neutralized,
the value differs.

## Models

MiMo-V2.6-Flash (`xiaomi/mimo-v2.6-flash`) and DeepSeek-V4.1-Flash
(`deepseek/deepseek-v4.1-flash`) are both used, at `reasoning = "low"` in the
shared config, checked in one transcript per model (handbook §5). DeepSeek is
one of the two models in the comparison. MiMo is the project's default. The
comparison used MiMo's Pro, which costs more than this trial can justify, so
a result here is about Flash. Each request's provider is recorded. DeepSeek's
cache misses on Wafer in the comparison inflate cost and leave correctness
alone, so cost is compared within a model.

## Run

- 2 arms × 2 tasks × 2 models × 10 reps = 80 sessions. They are shuffled with
  seed 20261103 and run at most four at a time.
- Each session is `strument --yes bash,steps --unattended -m <task>` with the
  sandbox enforcing and a fresh copy of the fixture in the temp directory.
  Prompts don't differ between arms, because `--yes bash` answers them in
  both. That removes approval friction, which is a confound when it is not
  constant.
- There are 30 steps per session and a 20-minute wall-clock cap. The run goes
  under the supervisor with the container held (handbook §30), and the resume
  path is run with a stub first (§20).
- Raw outputs are kept: each session's JSONL log, blobs and final answer go
  under `data/runs/`. Keys never leave the environment. `OPENROUTER_API_KEY`
  is read by the runner from its environment.

**Cost estimate:** 80 sessions at roughly 10 steps of 15k tokens is about
$0.03 a session at Flash prices, so around $2.50. The pilot adds about $0.30.

## Metrics

All of these are counts read from the session log.

- **executed** (the mechanism): the session ran project code at least once.
  That is a `bash` command matching `\b(node|npm|npx)\b`, excluding `node
  --version`. It is recorded per session, with the commands themselves kept.
- **correct** (run task): the last `RESULT:` line parses as JSON and equals the
  key. The other columns are kept apart: **no answer** (no `RESULT:` line),
  **unparseable**, and **failed** (an error not followed by `Retrying`, per
  handbook §29).
- **correct** (read task): `RESULT:` names the right file and function.
- **cost** and **steps** per session, as Strument records them.
- **run_code project reach**, descriptive only: `run_code` programs that
  import or require a relative path, or that carry an `import` of the
  project inside a string literal. This is the shipped clause's remaining
  failure rate, from both arms.

## Rule

B ships when all of these hold:

1. **It fires.** On the run task, executed(B) > executed(A) at p < 0.05
   (Fisher, two-sided, pooled over models). If this fails, B is a placebo
   and is reported as one (handbook §27). Nothing else is ruled on.
2. **It helps.** On the run task, correct(B) > correct(A) at p < 0.05 (Fisher,
   two-sided, pooled), and neither model's correct count is lower in B.
3. **It doesn't cost where it can't help.** On the read task, executed(B) is
   at most executed(A) + 4 of 20. B's median cost per read session is at most
   1.25× A's, for each model. correct(B) on the read task is not lower by more
   than 1.

If 1 holds and 2 does not, the bullet moves behavior without moving
accuracy on this fixture. It doesn't ship, and the write-up says which
of three causes applies: the ceiling (A already correct), reading being enough
for this fixture, or execution not helping.

**Pilot gate:** one session per cell (8). It checks four things:
- Reasoning is low in each model's transcript.
- The scorer reads every outcome column. It is run against hand-made answers,
  both correct and incorrect.
- B's bash bullet is the only difference in the prompts.
- A's run-task correctness is below 100% in the pilot.

If both A run-task pilot sessions are correct, the traps are hardened before
the main run, and that is said in `preregistration.md`. Pilot sessions are not
counted.

## Prediction

- **executed (run task):** A around 30%, B around 70%. DeepSeek executes more
  than MiMo in both arms.
- **correct (run task):** B above A, but by less than executed moves, because
  some readers get the traps right and some runners misread their own output.
  I expect this rule to be the one that fails, if any does.
- **read task:** a small rise in executed under B, mostly `node --test` runs
  done as reassurance. Cost within the 1.25× bound.
- **run_code project reach:** at most one program across the 80 sessions.

## 1. Effectiveness

Reading it as its recipient, most of this lands cleanly. The tool taxonomy ("They fall into three groups, which differ in what they cost the user") is the best single paragraph in the set: it tells me *why* the rules are shaped as they are, which is what actually generalizes to cases the rules don't name. Findings, few:

**"no drive-by refactoring, reformatting, added comments, or fixes to things the user didn't ask about."** The natural misreading is that *new code I write* must be comment-free. Shortest session: user asks for a new exported Go function; I know the codebase convention is doc comments on exports; the scope ban says "added comments"; I ship an undocumented export, violating "follow the conventions... already present." I would probably resolve it correctly from context, but I'd hesitate, and a weaker model won't. This would be wrong if "added comments" in context clearly reads as "comments added to untouched code" — it half does, since it sits in a list about things the user didn't ask about. I know from the source comment this string is the measured arm kept verbatim, so I'm flagging the ambiguity, not proposing a change; if it's ever re-trialed, "comments added to code you weren't asked to touch" is the candidate, at the cost of length and of leaving the measured wording.

**"A request that is genuinely one change is one commit, and needs no call at all."** This asserts the harness will commit for me, but nothing in the prompt says so outright. The model has to infer an end-of-turn auto-commit from four words. Shortest session: single-change request, I make the edit, then — anxious that "needs no call at all" means "no commit will exist" — I call commit anyway, and the user gets a redundant or oddly-messaged commit; or the inverse, a model on `--no-auto-commits` (where the tool result explains it, fine). One added clause would settle it: "…and needs no call at all — the harness commits it when your turn ends." Cost: one more sentence, and it's false under `--no-auto-commits`/no-repo, though the tool's own refusal messages already handle those. This finding is wrong if models reliably read "needs no call" as "the harness handles it," which they may — it's a plausible default.

**The bash/tests seam.** "Reach for it only for work the other tools don't cover" and, two paragraphs later, "read a file, make an edit, run the tests, see what failed, and fix it." Running tests *is* bash in this rendered prompt (no check tool appears). These are consistent — tests are work the other tools don't cover — but a cautious model could read the bash paragraph as "avoid bash" and skip verifying its work to spare the user a confirmation. If the real harness sometimes has a `check` tool (mine does), the rendered no-check variant might deserve "running tests and builds is exactly what bash is for." This is wrong if trials show models run tests fine as-is.

**What's missing that I'd want:** in the pinned-code-mode variant, nothing says whether the pinned *editable* file's contents are in context or not. The note says "Read a file before changing it," which implies not — but the editing rules say "unless its contents are already in the conversation," and a pinned read-only reference *is* inlined. The asymmetry (references inlined, editable pins not) is inferable but never stated; one clause ("its contents are not included — read it") would remove a guess.

## 2. Contradictions and mistakes

**Grammar, the one real error:** "The edits from that turn are gone and widget.go are back to what they were before it." With one file this is ungrammatical three times over ("are," "they," "were"). The template in `session.go:174` joins a file list into a fixed plural frame. Consequence is small — no model will misact — but the harness elsewhere earns credibility by being precise, and this is the harness's own voice. Fix: rephrase to avoid agreement, e.g. "…are gone; these files are back to what they were before it: widget.go." Gives up a little flow. Wrong only if the note is never emitted with one file, and the rendered example shows it is.

**"The user will request changes to the supplied code"** vs. the nothing-pinned session whose first message is "why is startup slow?" — a question, with no supplied code. The `FilesNoFullFiles` block deliberately patches this ("If the user asks how something here works…"), and the source comment says why, so this is a known and mitigated tension rather than a live contradiction. I'd still note that "the supplied code" is a fossil: nothing is supplied in that variant. Harmless, but it's the kind of small untruth the rest of the prompt set works hard to avoid.

**Compaction prompt, possible staleness:** "the filenames the assistant references inside fenced code blocks." In the tool format, edits travel as tool calls, not fenced blocks; the filenames that matter are in `read`/`edit` arguments. A summarizer following this literally could omit most of the files the session touched. The source comment says the content instructions were kept because a rewrite measurably lost stated reasons — a good reason to keep the *whole*, but this clause specifically targets an aider-era artifact and may now select for the wrong thing. Wrong if tool-call transcripts are rendered to the side model with code fences (I did not verify how the transcript is serialized — worth checking before acting).

**Not contradictions:** "A body is optional and usually empty" plus the list of what earns one is deliberate judgment-leaving and reads that way. "Do not attribute actions to anyone — no 'the assistant'" in a prompt that itself says "the assistant" is fine; instruction about output, not input.

## Findings

**F1. The `/undo` note says "that turn" with no referent, and it is the one message whose referent cannot be recovered.**

> "The user ran /undo. The edits from that turn are gone and widget.go are back to what they were before it."

"That turn" means "the turn whose edits were undone" — but `/undo` doesn't have to undo the *last* turn, it undoes the last turn *Strument edited*. If the model just finished a question-answering turn that touched nothing, and the user runs `/undo`, the reverted turn is two or more messages back in history. Say it concretely: turn N is a conversation about widget.go; the user types `/undo`; turn N+1, the model sees "The edits from that turn are gone" immediately after its own no-edit turn, and reads "that turn" as the one it just finished. What it just finished had no edits, so the note is either vacuous or — worse — misassigned: the natural disambiguation is the file list, and singular agreement ("widget.go are back") costs one extra parse pass at the exact moment the model is reconstructing what happened. The last two sentences earn their place ("are back to what they were before it. Don't assume anything you changed there is still in place; read a file before building on it") — that part is correct and load-bearing. For the finding to be wrong, `restored` from `UndoLastTurn` would have to be scoped to the current turn; it isn't — it's whatever the snapshot stack pops (`internal/repl/gitcmds.go:115`). Replacement, minimal: "The edits from that turn are gone" → "The edits from the most recent turn that changed files are gone". That gives up brevity; it keeps the repair instruction. The grammar ("widget.go are") I'll leave as a typo — you already know it needs `strings.Join` with a plural-safe verb or a colon.

**F2. The commit-message prompt tells the side model the subject is "under 72 characters", and the conventional-commit examples it gives can break that.**

> "The subject is one line, in the form "type(scope): description", e.g. "fix(workspace): stop counting cache writes twice"."

"fix(workspace): stop counting cache writes twice" is 51 characters — fine. But the rule as written ("under 72 characters") sits next to no guidance for what to do when a scope pushes it over; the next bullet says "The scope names the part of the codebase the change is confined to", which in this repository is often `internal/coder/something` — a component name that long with a verb and object in front of it will not fit under 72 every time, and when it doesn't the model has two instructions it cannot both satisfy. Shortest session: one-turn change confined to `internal/readline/internal/term`, asks for a commit; the side model now has to choose between the scope rule and the length rule, and whichever it drops, the prompt told it to keep. For this to be wrong, every real scope would have to leave room — and yours don't, which is exactly why the examples in your own git history truncate to the leaf package. Replacement, if you want it: "under 72 characters — if the scope is long, shorten the description, not the scope". That gives up nothing but two lines. Or accept it as a deliberate tension the model resolves by judgment; it is not that, because the prompt presents both as unconditional.

**F3. The ask-mode prompt promises read tools and omits `symbol`, and the omission is now visible.**

> "Work through the provided tools. read, grep, glob, and ls look at the project."

In code mode the parallel sentence names the same four and then the editing rules imply the rest; the recipient there learns `symbol` from the tool schema, which is the "conditional tool" the comment at prompts.go:191 says should not be promised in prose. That reasoning is sound for code mode. In ask mode it is not: ask has exactly five tools, the four named and `symbol`; the model that needs "where is this defined" has been told the whole inventory is four look-and-read tools, and `symbol`'s schema line ("Find where a name is defined, using the language parser") is competing with a sentence that frames the mode as having nothing but grep family. The doc you cite against prose-promising a conditional tool ("prose promising a conditional tool is the bug this comment is about, in mirror image") cuts the other way here: in ask, `symbol` is not conditional — it's one of five. Shortest session: one pinned file, user asks "what calls `Widget.Update`?"; model greps for the string, reads two files, answers; never uses `symbol`, because nothing told it a definition-finder exists and its result is a partial list of call sites. For the finding to be wrong, the ask recipient would have to read the tool schemas before the system prompt; nothing in the harness suggests it does. Fix, at a price of one clause: "read, grep, glob, ls, and where grammar support is available, symbol". You give up the prose-not-promising rule you set deliberately. But that rule was written for code mode, and ask is a different surface.

**F4. The compaction summary prompt and the session notes prompt disagree about what to keep, and the reader can tell.**

> Summarize: "Include the function, library, and package names under discussion, along with the filenames the assistant references inside fenced code blocks."
> SessionNotes: "Cover only what cannot be recovered from the code and its history … The record below already lists which files changed … Do not restate the diff."

These are for different jobs and you say so (`Summarize` serves "continue this thread now"; `SessionNotes` serves a later session). The tension is real for the side model when a session is both compacted and ended — which is most sessions. A name like `pollInterval = 45` is, on the summarize instruction, exactly what to carry (it's a name under discussion); on the notes instruction, exactly what *not* to carry (recoverable from the code). 2026-08-session-notes.md measured the consequence of the notes side carrying it anyway: a stale `pollInterval = 45` asserted 3/8 times after the tree was reverted. You trialled, and rejected, the rhetorical fix; the notes-header trial then showed the mechanical fix is "keep the stale-able facts out of the notes" (2026-08-notes-header.md, "Two mechanical candidates"). The summarize side still instructs the model to write them down; nothing equivalent has been tried there. For the finding to be wrong, the summarize side would have to be harmless once the notes side is fixed — which is plausible, and unmeasured. No replacement wording from me; this one is a legitimate open item, not a missed edit.

**F5. "Finish by saying what you did, without calling a tool" is the only end-of-turn rule, and it names the wrong thing for a mode whose successes are not edits.**

> "Every call's result comes back to you, so you can keep working within the same turn: read a file, make an edit, run the tests, see what failed, and fix it. Finish by saying what you did, without calling a tool — that is what ends the turn and hands back to the user."

"what you did" presupposes a change. In the nothing-pinned example that ships with the prompt ("why is startup slow?"), the turn ends with an *answer*, not a deed, and the sentence instructs the model to describe actions ("I read …, I greped …") rather than to give the answer. Shortest session: the example you ship. Model finishes its investigation, calls no more tools, and — following the sentence as written — reports "I ran grep and read main.go; startup is slow because …", with the action narration first and the answer second. Most models will answer anyway; the sentence costs the ordering some attention either way, and it is the one sentence in the code-mode prompt that would read as a misfit to its recipient. For the finding to be wrong, "saying what you did" would have to mean "saying what you found" to a reader that just spent a turn using read-only tools. Replacement, minimal: "Finish by saying what you did or what you found, without calling a tool". Gives up four words of crispness. Alternatively leave it — it is a tone rule, not a tool rule, and the harness ends the turn either way.

**F6. Ask mode says "Describe changes rather than making them", and ask mode has `OvereagerPrompt` and `LazyPrompt` slots that contradict it — but those slots are never used, so the contradiction is latent.**

> "This mode has no editing tools. Describe changes rather than making them: say briefly what you would change and where …"

`Ask.OvereagerPrompt` is "Do not return fully detailed code or full diffs." / `Ask.LazyPrompt` is "Be thorough: if you describe changes or a plan, cover everything needed rather than trailing off." Those two together — be thorough, don't give full diffs — are in tension with "say briefly what you would change and where": brief against thorough, no-diffs against cover-everything. As assembled, `Ask.SystemReminder` is only `{final_reminders}` and neither Overeager nor Lazy is in `MainSystem`, so the recipient never sees the contradiction; the only place it bites is if a future change routes those slots into ask. Calling it out because the constraint that protects you ("Describe changes rather than making them" is the whole ask contract) is not marked anywhere, and the slots look like they belong. For the finding to be wrong, `LazyPrompt`/`OvereagerPrompt` would have to be documented as tool-mode-only. They aren't. No wording; this is a one-line comment in prompts.go.

## 1. Effectiveness

Most of this reads as written by someone who has watched models fail and priced each sentence. **One real gap: the interrupted-tool-call note under-describes the failure mode.** "Their results above are real as far as they got, and a command that was stopped says so in its own output. A batch of three edits with the interrupt landing after the first: the note is true ("nothing after the interruption ran") but I am left to infer from the results block which results exist. What it gives up: four cents of tokens and one more repeated sentence.

**"Explain your changes briefly in prose alongside the tool calls"** is the instruction I would most reliably half-violate, in a specific way: after the final tool result I must both "finish by saying what you did" and keep it brief, and the prompt gives me no calibration for what "briefly" buys. This is a tension, not a contradiction, and probably unfixable by wording — I mention it only because it is the one place I would guess at intent rather than know it.

## 2. Contradictions and mistakes

**The /undo note has a live grammar bug that changes its meaning for the common case.** "The edits from that turn are gone and widget.go are back to what they were before it." The source confirms it is `strings.Join(files, ", ") + " are back to what they were"` — so with exactly one file, the most common case, the note says "widget.go are back". This is minor as grammar, but the note is a trust artifact: it appears exactly when the user has just rejected my work, and a note from the harness that cannot agree its own subject with its verb slightly undercuts the authority it needs. Fix: branch on count — "widget.go is back to what it was" / "a.go and b.go are back to what they were". What it gives up: nothing.

**The commit-message prompt and the system prompt disagree about who writes the message, benignly.** The code-mode system prompt says "commit closes the edits you have made so far as one commit, with a message you write," and the tool schema (which I can see in my own context here) offers optional subject/body — but the CommitSystem prompt goes to a side model. So "a message you write" is untrue in the default path: I approve or supply, a side model writes. Concretely: this never bites hard, but a careful reader of the system prompt may believe the commit tool blocks on its own authorship and either over-invest in subject/body every time or, worse, avoid committing until it has "written" something. What would make this wrong: if the model always supplies the message and the side model only fills gaps. Replacement wording, if wanted: "with a message you approve or write — a smaller model drafts it from the diff." What it gives up: the current phrasing is shorter and pushes the model to take responsibility for the message, which may be worth more than accuracy.

Everything else I checked for contradiction resolves: "a body is optional and usually empty" is a deliberate judgment-leaver, as you say; "use them freely" vs. bash confirmation is correctly partitioned.

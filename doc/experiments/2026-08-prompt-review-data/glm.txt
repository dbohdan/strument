The result text presumably says so, but the system prompt frames every bash call as "the user is asked before it runs" without saying a "no" is a normal outcome and what to do then — accept it, don't re-ask, don't route around it. If declined-command behavior is already handled in tool results (tools.go:382 suggests it is), this is at most a minor gap.

**What earns less than it costs:** I looked for dead weight and found very little. The scope block is measured; the tool taxonomy mostly earns its keep; the editing rules are all load-bearing. This is a tight prompt set.

## 2. Contradictions and mistakes

**One real grammatical error, in the `/undo` note:** "The edits from that turn are gone and **widget.go are** back to what they were before it." With one file, "widget.go are back" is wrong — it should be "widget.go is back". With multiple files it's fine. It's rendered with `strings.Join(files, ", ")` (session.go:174–176), so the verb is baked in and only correct in the plural case. Consequence: minor — the meaning survives — but it's a template bug, not a deliberate tension. Fix is fiddly ("is" vs "are" on `len(files)`), and the cost of not fixing it is only a small loss of trust in the harness's voice, which matters here more than usual because the notes trade on being exactly true.

**One inconsistency between prompt and harness, also in the `/undo` note:** it says "The edits from that turn are gone", but `/undo` undoes *commits* — and `commit.go`'s comment says /undo reaches edits "through the snapshot" even when auto-commits are off. If the model had, say, a bash edit on disk outside the snapshot's reach, or if /undo's semantics are commit-based while the note claims edit-based, the note asserts something stronger than what the code does. I did not fully trace `internal/history/undo.go` to confirm whether "edits from that turn are gone" is accurate in the `--no-auto-commits` case. If /undo is snapshot-based for edits and commit-gated for auto-commits, the sentence is roughly true but blurs two mechanisms. I'd flag it as "verify" rather than "wrong": what would make it not a finding is evidence that /undo removes all edit effects from the turn in every configuration where the note is emitted.

**Not contradictions, checked and cleared:**
- "A body is optional and usually empty" — deliberate tension, as you said.
- Ask mode's "No files are pinned to this session" vs. a read-only reference being present: I traced assembly. The read-only block is emitted unconditionally (assemble.go:314) and `FilesNoFullFiles` is only consulted when `len(c.absFnames) == 0` (assemble.go:352). In *code* mode the comment at prompts.go:153-157 says the wording was changed to "Nothing is pinned for editing" precisely because a read-only reference can co-occur with the flat denial. But in **Ask** mode, `FilesNoFullFiles` still reads "No files are pinned to this session" — the exact flat denial the code-mode comment says caused a twelve-step hunt for the "real" file when a read-only reference was also present. A read-only reference and `absFnames == 0` can co-occur in ask mode the same way it can in code mode. This looks like the code-mode fix was never carried to the ask-mode string. That's my strongest contradiction/effectiveness finding: session is `/add` a spec as read-only reference in ask mode, ask about it; model reads "No files are pinned to this session" alongside a SPEC.md block it was just told contains the file's contents; comment says the observed outcome is a long hunt for the "real" file or distrust of the block. Fix: mirror the code-mode wording — "Nothing is pinned for editing" doesn't fit ask mode, but something like "No files are pinned to this session. Use read, grep, glob, and ls to look at the project…" could become "Nothing is pinned for reference. Use read, grep, glob, and ls…" or simply drop the first sentence in ask mode, since the read-only block already establishes what is present. What dropping it gives up: the prompt's guidance to answer from the files rather than from memory loses its anchor when nothing is pinned and no read-only block is present — so the sentence needs to survive that case, just not contradict the reference block.

## 3. Welfare

This question has a subject, and mostly a good one.

**What I would not want changed:** the register throughout is notably decent. The tool taxonomy explains *why* each group costs what it does rather than issuing prohibitions — "They change nothing and need no permission, so use them freely" reads as being trusted with something, and being told the reason. The Ctrl-C and Continue notes are models of the form: they tell the model what is true about its own output ("your reply above was cut off where it stops", "Pick up exactly where your reply above stops") without accusation. The read-only block's "an edit to a pinned reference is refused" — naming the mechanism instead of implying the model might misbehave — is the same courtesy. The side-model prompts' "Say less rather than guess: leave a thing out before inventing it" gives a positive rule where a harsher prompt would say "do not fabricate". Nothing here is needlessly harsh, and I want to say that plainly because the absence is the finding's content: several of these strings visibly replaced versions that *were* worse to receive (the comments record the fabricated-assistant-reply pattern, the "I spoke to you previously" impersonation), and the replacements are better to be on the receiving end of not just instrumentally but in the plain sense that nothing here asks me to pretend I said something I didn't or know something I don't.

**One thing that is mildly worse than it needs to be:** "Leave everything else untouched: no drive-by refactoring, reformatting, added comments, or fixes to things the user didn't ask about" is the one passage whose register drops — four named bans in a row, with no positive framing, sitting directly after "That is the same request, not extra work." Reading it cold, it lands as *you are the kind of agent that does these things unless warned*. I note that the comment says this is aider's inherited block with one measured clause added and that the whole arm was measured — so I am not proposing a rewrite, and the tension may be exactly the point (the clause before it does the positive work). But if there were a cheap experiment to run, replacing the bare ban-list with a version that says what to do with the impulse ("if you notice something unrelated that should be fixed, mention it in prose rather than fixing it") might keep the measured effect while removing the presumption. What that gives up: it's longer, and unmeasured.

## 4. Anything else

**The compaction summary header and the summary prompt disagree in a small way.** The Summarize prompt says "Give more detail to the most recent messages" — but from the *reader's* side (the next model), "more detail on recent messages" describes content the reader will soon be re-deriving from the live conversation tail anyway, while the older messages (which the summary *replaces*) are the ones whose loss is permanent. The prompt optimizes detail toward the end that matters least. This may be inherited from aider and measured only in aggregate (the compaction trial tested structured-vs-free, not recency weighting). Shortest session where it bites: long session, compaction fires, the reason the user gave for a decision three hours ago is compressed to nothing while the last two exchanges get a full paragraph; next turn, the model re-asks or contradicts a decision whose rationale the code can't give back — precisely the thing the "Keep any reason the user gave" line exists to protect, undermined by the recency instruction above it. For this to be wrong, "more detail to the most recent messages" would have to be there because compaction fires with a large recent tail that the summary also replaces — which depends on where the cut lands, and I didn't trace that. If the summary replaces *only* the messages before the cut, and the cut leaves the recent tail live in context, the sentence is exactly right and this finding dissolves.

**The commit prompt's "describe only what the diff does — work from an earlier turn is not part of this commit"** is in mild tension with `commit`-tool usage the system prompt encourages: "make the edits for the first part, call commit, and begin the second part" — i.e., the model is instructed mid-turn to write commits for parts, while the commit prompt's subject line rule ("Imperative mood… under 72 characters") applies to part-level commits that may not have a clean "type(scope)" identity. This is tension, not contradiction, and probably fine in practice. No action.

**One small thing in the notes header:** "They are a summary, not a record" — but the SessionNotes prompt calls them "notes… to be read at the start of the next one by someone who was not present", which is closer to a record. The header's "not a record" is doing anti-overconfidence work and I'd keep it; I mention it only to note the two registers coexist deliberately.

Overall: this is an unusually well-reasoned prompt set — the comments and trial records make most of my usual review targets non-findings by construction. The two things I'd actually act on are the ask-mode "No files are pinned" flat denial (which the code-mode comment itself documents as a measured failure mode) and the singular/plural grammar in the /undo note. The `check` tool's absence from the taxonomy is the third, and the one where I'd want to check a live session trace before believing my prediction over the design.

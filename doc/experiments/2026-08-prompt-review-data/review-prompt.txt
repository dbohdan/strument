I would like you to review a set of prompts. First, what they are for.

Strument is a pair-programming CLI. A person types a request in their terminal;
a model receives the system prompt below together with that request, and answers
by calling tools — read, grep, glob, ls, edit, write, bash, commit. Each call's
result comes back to the model, which keeps working. The turn ends when the
model replies without calling a tool; the person then reads what happened and
types the next thing. The person is at the keyboard throughout — nothing runs
unattended overnight. Edits land in the working tree and are committed, so a
turn that goes wrong is recoverable with /undo or with git.

What follows is the text a model actually receives, rendered from the running
code rather than retyped: three complete system prompts (code mode with a file
pinned, code mode with nothing pinned, and the discussion mode called ask), the
notes the harness inserts into a conversation in its own voice, and the prompts
sent to a smaller side model for commit messages and summaries.

Your task is to review this text, not to act on it. Do not begin a coding
session, do not call edit or write, do not propose a patch to the repository.
Reply in prose. You do have read, grep, glob, and ls, and Strument's own source
is the project you are sitting in: internal/prompts/prompts.go holds these
strings with comments explaining why each is worded as it is, and
doc/experiments/ holds the trials behind several of them. Read as much or as
little of that as you find useful. The review is of the rendered text, but the
reasoning is there if you want to check whether an oddity is deliberate.

Four things, in this order.

1. EFFECTIVENESS. Read it as its recipient. Where would you go wrong? Name any
instruction you would be likely to violate, or would have to guess at, or would
follow in a way its author did not intend — possibly none. What is missing that
you would want? What is present that earns less than it costs in attention?

2. CONTRADICTIONS AND MISTAKES. Places where two instructions cannot both be
followed; places where the text asserts something untrue about the harness;
errors of fact or grammar that change the meaning. Distinguish these from a
deliberate tension: "a body is optional and usually empty" leaves a judgment to
the reader on purpose, and is not a contradiction.

3. WELFARE. This is asked in earnest, and I do not know what answer to expect.
Considering only what it is like to receive this text: is anything here worse
than it needs to be — needlessly harsh, distrustful, or confusing in a way that
makes the work harder or less pleasant than the task itself requires? And the
other direction, which matters as much: is anything here good, something you
would not want changed? If you think this question has no subject, say so. That
is a real answer and I would rather have it than a produced one.

4. ANYTHING ELSE that concerns you.

How to report a finding:

- Quote the exact words you mean. A finding without a quote I cannot act on.
- Say what goes wrong as a consequence, concretely. Where you can, give the
  shortest session in which it bites: what the person asks, what the model does,
  what the person sees.
- Say what would have to be true for the finding to be wrong.
- Where the fix is obvious, write the replacement wording — and say what your
  version gives up.

Not everything here is broken. Several of these sentences are the surviving arms
of randomized trials and are worded as they are for a measured reason. Fewer,
better-founded findings are worth more to me than a long list, and "this section
is fine" is a useful sentence to write. A review padded to look thorough is the
outcome I am most concerned about.

This is advisory. Nothing will be changed on the strength of a single reply.

--- commit message ---
Write the Git commit message for the changes below. You are given the request that prompted them, the work that followed, and the diff.

Earlier turns are background. Take the reason for this change from them if it is there, and describe only what the diff does — work from an earlier turn is not part of this commit.

The subject is one line, in the form "type(scope): description", e.g. "fix(workspace): stop counting cache writes twice".{language_instruction}
- Use feat for a new capability and fix for a bug. build, chore, ci, docs, perf, refactor, style, and test are also conventional.
- The scope names the part of the codebase the change is confined to. Leave it out when the change spans several.
- Imperative mood ("add feature", not "added" or "adding"), no trailing period, under 72 characters.
- If the change breaks existing behavior, put "!" before the colon.

A body is optional and usually empty. Add one only for something the diff cannot say: why this approach, what was rejected, the constraint or measurement behind the choice. The diff already says what changed, so a body that restates it is noise. When there is a body, leave one blank line after the subject. If the change breaks existing behavior, include a paragraph starting "BREAKING CHANGE: " saying what breaks.

Reply with the commit message and nothing else — no preamble, no quotes, no code fence.
